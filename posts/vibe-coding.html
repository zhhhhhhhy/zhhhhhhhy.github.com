vibe coding：AI 已足够强，瓶颈在于怎么用

2026-10-04 # AI-native # 效率

最近在 AI-native 的圈子里反复听到一个词，叫 vibe coding。第一次听到时的第一反应是：这算不算一种偷懒？后来自己实打实操了一轮才发现，它和"偷懒"差了很远——它背后是一整套关于"人该怎么用 AI"的判断。这篇文章，是我对这组判断的整理。

01什么是 vibe coding

vibe coding 这个说法来自 Karpathy（2025 年提出）：你不再逐行手写代码，而是把意图说清楚，让 AI 主导生成、运行、迭代，人退到"指挥 + 验收"的位置。

它不是"让 AI 写，人躺平"，而是重新分工：实现交给机器，判断留给人。真正要修炼的，不是写代码的手感，而是"说清楚要什么"和"判断做得好不好"这两件事。

02AI 和人，谁更强

在写代码这件事上，结论其实很干脆：AI 的能力已经远超于人。它速度远大于人，产出质量在多数场景不逊于平均水平，而且不知疲倦。

既然 AI 更快也更强，人就不该成为限制它的环节。那种"每一行都要人盯着改"的做法，本质是把最强的工具用成了最慢的方式。人在这个系统里真正的价值，不在"写得比 AI 好"，而在"决定做什么、做到什么程度算好"。

03vibe coding 需要什么

既然瓶颈不在 AI 的能力，那在哪里？在我自己的实操里，它落在三件事上：

// vibe coding 的三要素

① context（上下文）——AI 的输出质量，高度取决于它看得见什么。上下文给得越充分，它越不容易凭空发挥、越少跑偏。
② 意图（intent）——AI 不会替你决定你要什么。目标、边界、期望的效果，必须由人清晰化地交出去。意图含糊，AI 只能猜，猜就必然偏。
③ 评估（evaluate）——也是最重要的一件。如果没有"做成什么样才算好"的标准，AI 根本不知道何时该停、该改哪里。

这三件事里，前两件是"给足输入"，第三件是"守住输出"。恰恰是最难、也最容易被忽略的第三件，决定了一个人 vibe coding 的水平。

04过程交给 AI，结果交给人的判断

AI 并非没有边界。过去它没有"眼睛"，没法亲眼评估自己的输出；现在它有了视觉，已经能做一定程度的自检。但最后一道评估，仍要由人握住——不是因为人写得更好，而是因为产品要由人来用。

一个人的初始设计必然是有限的，没法要求最开始的设计完全达标。真正推动产品前进的，是来自真实使用的反馈：没有人用，就没有反馈；没有反馈，产品就不会进步。

所以最好的协作方式是 human in loop——中间过程不 loop，结果上人一定在 loop：人负责最初的设计，也负责最终的验收。这和 fake work 是同一个根：评价（evaluate）才是驱动进步的那一环。fake work 里我们缺的是对自己的评价，vibe coding 里我们缺的是对结果的评价。

05还没解决的一件事：边界验收

但把"最终验收"交给人也带来一个新问题：人的验收能力同样有限。

一个大型项目里，边界情况浩如烟海——极端的输入、并发的冲突、未曾预料的组合——单靠一个人去逐条覆盖，几乎不可能。人很容易验不到这些边界，于是只能靠堆大量的人去验收边界。

// 留一个还没想透的问题 在 AI 时代，边界验收这件事，能不能不再靠"人海"来解决？是不是可以让 AI 自己构造边界测试、自己去找失败案例，人只做最终的确认？——这个问题我还没有想透，先记在这里。它或许会成为 vibe coding 在"验收"这条路上，下一个真正值得解决的问题。
